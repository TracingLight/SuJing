# 溯境维护与发布说明

本文是日常操作清单。工程结构和组件职责见 [项目工程指南](./项目工程指南.md)；Markdown 和 Butterfly 标签见 [写博客-Markdown语法](./写博客-Markdown语法.md)。

## 新建文章

1. 确认 Node.js 满足仓库要求，首次使用先执行 `npm ci`。
2. 用 `npx hexo new post "标题"` 创建文章，或在本机管理台新建。
3. 填写标题、日期、分类、标签、摘要和封面；正文不要重复写一层 Front Matter。
4. 图片原图放 `assets/user/`，处理后的图片放 `source/img/posts/` 或 `source/img/covers/`。
5. 运行 `npm run server` 预览，检查文章页、文章列表、归档、移动端和站内链接。
6. 执行 `npm run check` 和 `npm run check:performance-build`。

## 修改首页、短讯、歌单或相册

- 首页布局和文案：`source/index.md`。
- 关于页：`source/about/index.md`。
- 短讯：`source/_data/notes.yml`。
- 歌单：`source/_data/music.yml`，音频通常在 `source/media/music/`。
- 相册：`source/_data/gallery.yml`，图片放站点图片目录或使用 R2 URL。

修改 YAML 后检查缩进、日期格式和数组结构；构建失败时先看第一条 YAML 解析错误，不要直接编辑 `public/site-index.json`。

## 批注与专栏

在管理台编辑文章时，先选中正文中的词语或句子，再点击「插入批注」并填写说明。生成的 Markdown 形如：

```markdown
{% annotation "说明 C++ 生命周期或背景" %}std::vector{% endannotation %}
```

批注内容保存于文章正文，重新打开文章后仍可继续编辑。发布前用 `npm run server` 检查桌面悬浮、键盘焦点和移动端点击效果。

主导航中的“专栏”会悬浮显示五个标签，点击后进入对应的独立页面，例如 `/columns/cpp/`。专栏配置在 `source/_data/columns.yml`，当前固定为 Unity、C#、C++、计算机基础、设计模式。文章的分类或标签与专栏名精确匹配（忽略大小写）后自动进入对应页面；同一文章可以出现在多个专栏。不要手工修改 `public/site-index.json`，修改配置或文章元数据后重新构建。

## 图片操作

本地站点图片：

```powershell
npm run admin
```

在博客管理按钮中上传，默认写入本地 `source/img/covers/`。需要长期远程存储时：

```powershell
npm run image:upload -- assets/user/example.webp screenshots
```

命令输出的 Markdown 才是可粘贴到文章的最终引用。上传前应压缩大图；工具超过 2 MB 会警告，R2 Worker 使用一年不可变缓存。

## 本地管理台故障

| 现象 | 检查 |
| --- | --- |
| 没有“管”按钮 | 确认运行的是 `npm run admin`，并打开启动窗口打印的实际博客地址；端口可能是 `4000` 以外的顺延端口 |
| Token 无效 | 使用启动窗口当前显示的 Token；不要手动改 `.sujing-admin-token` 后复用旧窗口 |
| 8787 被占用 | 读取启动日志中的实际端口，或设置 `SUJING_ADMIN_PORT` |
| 预览打不开 | 查看启动日志中的博客地址和 Hexo 输出；`4000` 被其它服务占用时启动器会自动顺延，重复启动时会复用可识别的本站预览 |
| 评论管理不可用 | 检查 `.sujing-comments-admin.json` 的 Token 是否与 Worker secret 一致 |

## 发布前后

发布前：

```powershell
git status --short
npm run check
npm run check:performance-build
```

发布：

```powershell
npm run publish:site
```

发布脚本要求当前在 `main`，会先同步检查 `origin/main`，构建、裁剪、验收后提交并推送全部未被忽略的修改。没有文件修改时仍可能推送本地尚未上传的提交。

发布后：

1. 在 GitHub 确认提交已经到达 `main`。
2. 在 Cloudflare Pages 查看新部署状态。
3. 打开主域名检查首页、最新文章、图片、统计和留言。
4. 若 Pages 构建失败，保留本地提交，修复后再次运行发布命令。

## 资源下线

删除 `source/` 文件后，在 `scripts/site-redirects.js` 添加旧 URL 到 `GONE`，再运行构建验收。只删除源文件会被 Pages 的历史文件回退机制掩盖，线上可能继续返回 200。

## 版本与依赖更新

依赖更新应修改 `package.json` 和 `package-lock.json`，在干净的 Node 22 环境执行：

```powershell
npm ci
npm run check
npm run check:performance-build
```

Hexo、Butterfly、`sharp`、`wrangler` 的升级会影响构建、图片处理或部署；升级后要额外检查主题标签、响应式图片、R2 上传和三个 Worker 的部署命令。不要删除锁文件后重新安装来解决单个包的问题。

- 修改文章 Front Matter 字段、永久链接、图片目录或上传策略；
- 修改发布脚本的分支检查、构建步骤、裁剪规则或推送行为；
- 修改前端统计、评论、音乐或 PJAX 的生命周期；
- 已知限制、回滚方式或验证命令发生变化。
